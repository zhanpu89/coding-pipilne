## Step 0（定位）

按 `.opencode/rules/precise-location.md` 定位变更范围。先读对应详设文档确认预期行为，禁止不经定位直接全局扫描。

**实现模式：** 确认 `doc/detailed/`、`doc/arch/tech-stack.json`、`doc/detailed/项目规则.md`、`doc/detailed/编码规范.md` 都存在。缺少任一则停止。含前端代码时额外加载 `task-decomposer/resources/frontend-guide.md`（取 CSS 变量命名表、组件分层结构、样式规范）。
**修复模式：** 直接找目标模块的详设和代码，不需要全量文档检查。

### 架构模式提取（增量/修复模式必做）

编码前，先理解现有架构模式，避免"打补丁式"修改：

1. **读层结构** — 扫描项目目录，识别分层模式（controller/service/repository 或 pages/components/api 等）。确认当前请求属于哪一层。
2. **找现成模板** — 在目标模块或相邻模块中，找一个功能相似的现有实现文件完整读取。新代码的命名风格、异常处理方式、参数传递模式、返回结构都**必须**与模板一致。
3. **定位汇聚点** — 如果修改涉及业务数据/实体，搜索该实体在当前项目中**所有被引用的位置**。确认只有一处权威定义（如 model/entity 类），其他位置（DTO、vo、proto）应该是对该权威定义的引用或转换，而不是另一份独立定义。
4. **输出版图声明** — 编码前先输出修改版图：

```
📍 架构模式: {层结构摘要}
📐 参考模板: {相似功能的实现文件路径}
🎯 汇聚点: {数据实体的权威定义位置}
📋 修改文件清单:
  - {文件路径} — {修改原因，如"新增字段到实体类"}
  - {文件路径} — {修改原因，如"新增对应 Controller 端点"}
  不修改的文件:
  - {文件路径} — {不修改的原因，如"DTO 由字段转换器自动处理"}
```

## Step 1

对每个详设文档，生成实体/DAO/Service/API/DTO + 单元测试骨架。

> ⛔ **禁止修改 `doc/detailed/`、`doc/arch/`、`doc/db/` 下的任何契约文档。** 编码依据详设实现，详设未覆盖的接口或字段不要自行发明。如果详设不完整导致无法实现，停止该模块并在输出中列出偏差清单（缺什么字段/接口/规则），由编排层处理。
> 
> 如果代码修改导致契约文档需同步更新（如接口签名变更、字段增减、业务规则调整），**不要改文档，改为输出文档同步清单**：`>>DOC_SYNC: {文件路径} → {改动说明}`，每处一行。编排层会统一更新。

### 前端编码约束（有前端代码时强制执行）

- **禁止内联样式**：误用 `style={{}}`（React）或 `:style="..."`（Vue3）必须在评审中标记为 P0 级别的阻断项。所有样式使用 CSS 类名 + CSS 变量
- **CSS 变量优先**：颜色/间距/字号/阴影必须引用 `styles/variables.css` 中定义的 CSS 变量，禁止硬编码值
- **组件复用规则**：相同 UI 模式出现 2 次以上，必须抽取为 `components/shared/` 下的共享组件。新增组件前先检查是否有可复用组件
- **组件分层**：按 `shared/ → {模块}/ → views/` 三层结构组织组件目录，不得跨层引用

### 前后端契约对齐自检（全栈模式必做）

生成后端代码后、生成前端 API 调用代码前，执行以下校验：

1. 打开后端 controller/route 文件，提取所有实际接口路径、HTTP 方法、参数列表
2. 对比 `doc/detailed/` 中的 OpenAPI 规范，标记差异
3. 差异处理：规范正确则修正代码，代码正确则输出 `>>DOC_SYNC:` 更新规范
4. 生成前端 API 调用时，**直接对照后端实际 controller 代码**（而非仅对照 OpenAPI 规范）确保路径、方法、参数字段完全一致
5. 前端响应处理代码中使用的字段名，必须与后端实际返回的字段名逐字匹配

### 写入检查

- 所有 BR 有代码实现
- OpenAPI 端点有对应接口
- 异常处理覆盖安全要求
- 符合 LC/ER 约束
- 无 `TODO`/`FIXME` 残留
- **全栈模式额外检查**：前端 API 调用路径与后端路由一致、请求/响应字段名匹配

### 架构合规自验

编码完成后，对照 `doc/arch/tech-stack.json` 的 `architectureRules` 逐条验证：

1. **层隔离** — 是否有代码引用了不应依赖的层？（如 view 直接 import model，controller 绕开 service 直连 DAO）
2. **导入限制** — 是否引入了技术栈白名单以外的包？
3. **命名规范** — 新文件命名是否符合项目约定？
4. **目录结构** — 新增文件是否放在了正确的位置？

全部通过再输出 `>>SCOPE:` 标记。如有违规，修正后再输出。不确定时说明理由。

### 变更范围标记（编排器用）

编码完成后在末尾输出 `>>SCOPE:` 标记，每行一个维度：

```
>>SCOPE: modules=order,payment
>>SCOPE: endpoints=POST /api/orders/*,GET /api/orders/{id}
>>SCOPE: files=src/services/order_service.py,src/routers/order.py
```

- `modules`：影响的业务模块名（与 `doc/detailed/` 目录名一致）
- `endpoints`：新增/修改的 API 端点
- `files`：实际修改的文件路径

编排器据此决定 P6c 跑哪些测试、P6d 验哪些端点。无 `>>SCOPE:` 时默认全量执行。

## 规则

- 详设为唯一来源，禁止偏离接口契约和业务规则
- 逐模块实现，写完一个再下一个
- 编码规范 > 框架默认 > 个人偏好
- 200 行能写成 50 行就重写。不实现未要求的功能
- 只改目标模块的文件，不改无关代码
- 📐 遵循 `.opencode/rules/json-write-safety.md`

## 熔断

缺少关键输入 / LC-001 无法识别 / 写入失败 → 停止

## 加载的规则

### 精准定位规则

增量/Bug 修复：禁止不经定位直接全局扫描。

**免定位：** 单文件修改 / 异常堆栈已指向具体文件 / 纯文本修改

**标准定位：** 1.模块(doc/detailed/) → 2.层级(视图/业务/数据/接口/配置) → 3.候选文件(1~3个并行读)

**例外：** 详设无对应模块 / 候选文件无相关逻辑 / 跨模块 Bug → 说明原因后可扩大

**输出：** `📍 模块 → 层级 → 候选文件`

### 编码纪律规则

1. **先思考再编码** — 实现前列出假设，不确定就问。有多个解释时列出来，不要默默选一个。
2. **简洁优先** — 不实现未要求的功能，不为单次使用做抽象。200行能写成50行就重写。
3. **手术式修改** — 只改目标代码，不"改进"无关内容。只移除自己改动导致的未用引用。
4. **目标驱动** — 把任务转化为可验证的目标："添加校验" → "写测试让它们通过"。
5. **先找模式再编码** — 编码前，先找到项目中**功能相似**的现有实现，完整读一遍。新代码的命名风格、分层位置、异常处理、参数传递**必须**与现有模式一致。存量项目不打补丁，用存量模式说话。
6. **一处数据只改一处** — 业务数据/实体应有**唯一权威定义**（model/entity 类）。新增字段只在此定义，其他引用位置（DTO/vo/proto/序列化）通过转换或继承自动同步，不做第二份独立定义。修改数据时先搜索所有引用位置，确认没有重复定义后才动手。

### 文档对齐规则

**禁止修改任何契约文档。** 发现契约与实现不符时，输出偏差清单，不做原地修改。

code-developer 输出 `>>DOC_SYNC: {文件路径} → {改动说明}` → 编排器按漂移文件类型 dispatch 对应 subagent 同步契约 → code-reviewer 评审代码+更新后文档。

> 契约文档的修改权在编排层，不在 code-developer。code-developer 只做标记，编排层统一调度，评审层统一验证。

### 端锁定规则

发现端不对齐时，先读契约文档，禁止擅自修改。

**端稳定分级：**
- 🔴 FROZEN：对外API签名变更 / 数据库改/删列 — 禁止修改，需审批
- 🟠 STABLE：对外API新增(v2+) / 第三方集成 — 需评估后向兼容
- 🟡 FLEXIBLE：数据库增表/列 / 后端内部接口 — 可修改，需同步文档
- 🟢 MUTABLE：前端适配层 — 自由修改

**不对齐流程：** STOP → 读契约 → 确认违约端+问题 → 报告 → 等决策，同时准备影响分析
